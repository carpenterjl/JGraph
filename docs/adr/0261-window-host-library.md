# ADR 0261 — The window host as a library, and a deployed component's figures in windows

## Status

Accepted, 2026-10-24. Compiler and SDK plan, stage K5.

## Context

Until K5 the figure window, the service that opens one per figure, theming, the native dialogs,
printing and the run that keeps `-batch -showfigures` alive until its last window closes all lived
inside the `JGraph.Application` WinExe. A deployed component (K4) made, counted, exported and
printed its figures but showed none (open item 177). K5 moves the window host into a library, so
that JGraph's application references it unchanged and the JGraph Runtime can show a component's
figures and uifigure apps in any process that can run WPF.

What R2025b does was measured first, by `record-k5.ps1` (`tools/matlab-checklist/compiler-probes`).
`k5.m` was built as the .NET assembly K5 and a C# client (`src/k5client`) called it. No window was
shown: the probe's figures are invisible.

- **A component's events run between calls (`k5_client`).** A timer one call started (five ticks,
  0.1 s apart) ticked on while the client slept with no call: tick 1 before the call returned, ticks
  2–5 and the stop while the client slept. The ticks also ran inside a call that paused, and inside
  one that computed without pausing.
- **`WaitForFiguresToDie`** returned at once with nothing open (0.0 s) and with only an invisible
  figure open (0.0–0.1 s).
- **The runtime's end.** With an invisible figure left open when the process ended, R2025b wrote to
  standard error:

  ```
  Warning: 1 invisible figure(s) at MATLAB Runtime termination.
   Figure ID(s):

  Name: k5 invisible

  If your application has terminated unexpectedly, please note that
   applications generated by the MATLAB Compiler terminate when there are no
   visible figure windows.
  ```

  The ID list was empty, though the figure was number 1. `close all force` had closed the figure in
  the client's first run; the warning there came from a figure the probe had not closed.

## Decision

### `JGraph.Runtime.Desktop` (new project, net8.0-windows, WPF)

- **Moved out of `JGraph.Application`, with history:** `FigureWindow`, `FigureWindowService`,
  `FigureWindowBinding`, `FigureViewModel`, `ObservableObject`, `RelayCommand`, `Theming/`,
  `Printing/`, `Import/` (the import wizard of the figure's toolbar), and the figure services
  (`AppScriptFigureFiles`, `AppScriptNativeDialogs`, export, document, data import, the sample
  figure). Their namespaces moved from `JGraph.Application` to `JGraph.Runtime.Desktop`.
- **Three seams, so the library needs neither the IDE nor dependency injection:**
  - `IFigureWindowShell` replaces the view model's script, options and settings services. The
    application's `IdeFigureWindowShell` opens its editor and Options dialog and names the theme
    its settings prefer. A deployed program's `DeployedFigureWindowShell` offers neither, and the
    toolbar's Script… and Options… buttons are hidden.
  - `FigureWindowService` takes a factory for its windows in place of the container.
  - `WindowedBatchRun` is the `-batch -showfigures` run, moved out of `App` unchanged: the session
    that outlives its script, the idle pump, the exit code kept until the last window closes.
- **More than one service per process.** The hooks the engine reaches the windows through (window
  bounds, the frame sink, the native dialogs, `uihtml`'s host) are installed once, and answer from
  every live service's windows. The runtime has one service per component, because each component
  numbers its own figures: two components' figure 1 are two windows.
- **`DesktopHost`**, the runtime's window host. In a process that already runs a WPF application,
  the windows join it on its thread and carry the theme themselves, so the host's look is left
  alone; there, showing and closing is queued rather than waited for, because the host's thread may
  be waiting for the very call that asked. In any other process a background STA thread is started
  for them with an application of its own, styled as the IDE is.

### A window's reports run in their component's state

The engine keeps the graphics handles, their callbacks and the callback queue in statics that the
runtime swaps per component (K4, `JgsProcessState`). A window reports what its user did from its own
thread, so a click on one component's window could otherwise be looked up, and queued, in whichever
component happened to be live.

- **`ScriptGraphicsCallbacks.Router`** (internal, null in the application). Every report goes
  through it: button presses, keys, motion, the wheel, resizes, menus, toolbars, component values,
  context menus, and two reports that were the window's own code before, `RequestClose` (the close
  box asking a `CloseRequestFcn`) and `NotifyWindowClosed` (the figure retired when its window closes).
- **The runtime's router** runs a report at once, under the lock that guards the swap, when its
  figure's component is the live one, as the application does. Otherwise it posts the report to the
  engine thread, which makes that component live first.
- **What must answer at once** answers conservatively when the component is not live. The close box
  keeps the window, asks the component, and closes it then if nothing answered. A right-click shows
  the built-in menu in place of the object's `uicontextmenu`.
- **The callback queue is per component now.** `JgsProcessState` moves the queued events out with
  the rest, and puts them back ahead of anything new.

### Between calls: the engine's idle work

- **`EngineThread.Idle`** runs after every item of work, and again when the next timer is due. It
  delivers each component's queued callbacks and runs its due timers with its state in place
  (`JgsReplSession.RunIdle`, the idle prompt's drain plus the timers). It runs after every item, not
  only when the queue is empty, so a client calling without pause does not starve its windows.
- **The event queue's pump** posts a no-op to the engine thread, which is enough to wake it.
- **Timers between calls** follow from this, as `k5_client` measured, with or without windows.
- **A figure's components made before the window host existed** get their first frame when the
  figure is first shown. The first show is what starts the host, and frames are taken only when a
  sink is there to receive them. Each component swapped back in also makes the next statement
  boundary rescan its figures for frames left waiting (`ScriptComponentFrames.Rescan`).

### What a component has now

- **Its figures in windows** (`JgRuntime.ShowFigure`, `IRuntimeDesktop`), closed with `close` and
  `delete`, retired when the session ends.
- **`Component.WaitForFiguresToClose`**, R2025b's `WaitForFiguresToDie`: it waits while any of the
  component's windows is on screen, and returns at once with none, or only invisible ones. It refuses
  on the windows' own thread, where they could never close.
- **`waitforallfiguresclosed` inside a call** waits for the component's windows, since a window host
  delivers its events.
- **Figure files** (`RuntimeFigureFiles`). `savefig`, `openfig`, `exportgraphics`, `print` and
  `getframe` were refused in a library component since K4, which gave it none. They are the
  launcher's now, and the window host's print dialogs, clipboard and `exportapp` once it is running.
- **The termination warning.** `JgRuntime.Terminate` writes R2025b's warning for the invisible
  figures still open, with JGraph's runtime named as in the start line. The runtime now also
  terminates when the process ends, if the client never called `Terminate`, waiting at most 5 s for
  a call still running. That also closes the `-logfile`.

### Found by name

`JGraph.Runtime` stays free of WPF (decision KO5). The first time a component shows a figure it
loads `JGraph.Runtime.Desktop`, from the process's own assemblies or from beside itself (the runtime
folder's `bin`). Where the assembly is missing, or the process does not run on the Windows desktop
framework, nothing is shown, as before. `installer/publish-runtime.ps1` publishes the host into
`bin\win64`. WPF itself still comes from the desktop framework, not from the folder.

## Consequences

- **K6's windowed programs (`mcc -e`)** run on `WindowedBatchRun` and `DesktopHost`. Its launcher's
  runtimeconfig names the Windows desktop framework.
- **K8 and K9** give `WaitForFiguresToClose` MathWorks' names (`WaitForFiguresToDie`, the Data API's).
- **JGraph's application** behaves as before. Only its project references and the namespaces of the
  moved types changed.

## Measured

- **`DesktopRoutingTests`** (8), with a stand-in window host recording what it is asked:
  - two components' figures go to two windows, each numbered 1;
  - a click reported from another thread runs its callback in the component that owns the window,
    whether that component or the other is live;
  - the close box asks a `CloseRequestFcn` in the right component, and closes once asked where there
    is none;
  - `WaitForFiguresToClose` waits while a window is on screen;
  - `waitforallfiguresclosed` in a call ends when the window closes;
  - `exportgraphics` writes its file in a library component;
  - terminating retires each component's windows.

  The eighth runs R2025b's own `k5.m` call for call as `k5client` did, and matches it: tick 1 before
  `started`, ticks 2–5 and the stop while the client sleeps, five ticks across a pause and across a
  busy loop, `WaitForFiguresToClose` at once both times, and the termination warning.
- **The rest of the touched areas pass**: 668 tests in the runtime, deployment, startup, callback,
  timer, wait, dialog, uifigure and app-designer classes, and the four compiler-stage parity
  fixtures (k1, k2, k3, k3b).
- **The window check** (`tools/runtime-checks/run-k5window.ps1`, JGraph's windows only, UI
  Automation patterns only), five times in a row:
  - **A console client:** two components in one process, a uifigure app titled `k5 app of a` and a
    figure titled `Figure 1: k5 plot of b`. The figure's toolbar is there without Script… or Options….
    Pressing the app's button ran its callback while the client made no call, and closing each window
    ended `WaitForFiguresToClose` with the figure gone. Exit code 0.
  - **A WPF client:** the same, with the windows joining the client's own application.
  - **The application:** `-batch -showfigures` with a figure and an app. The figure's toolbar has
    Script… and Options…, and the app's button closed both windows, so the run ended with exit
    code 0 and the callback's line on standard output.
- **The runtime folder** publishes at 168.3 MB with ReadyToRun (K4's was 166 MB), every anchor
  present and no WPF assembly in `bin`.

## Divergences

- **The termination warning names JGraph's runtime**: `Warning: 1 invisible figure(s) at JGraph Runtime termination.` where R2025b names the MATLAB Runtime.
- **A right-click on a figure of a component that is not live shows the built-in menu**, not the object's `uicontextmenu`, which is resolved now or not at all.
- **The close box of a figure of a component that is not live** keeps the window until that component has been asked, even where it has no `CloseRequestFcn`.
- **A client process that does not run on the Windows desktop framework shows none of its components' figures**; they are made, counted and exported as before.
- **On a WPF client's own thread a component's windows open after the call that made them**, so a call from that thread that waits on them (`uiwait`, a blocking dialog, `waitforallfiguresclosed`) never ends; such a client calls `CallAsync`.

## Still open

- Item 179: .NET events and device callbacks between calls are drained in the live component, not
  necessarily their own; their queues are not yet per component.
- Item 180: a client that does not run on the Windows desktop framework gets no windows without a
  word, and loading the host from beside the runtime, rather than from the client's own
  assemblies, is not yet exercised by a real client (K6's launcher, K9's).
- Item 181: UI Automation reads a window's components once. A window read before its components
  arrive keeps showing it empty, both to a screen reader and to the window check, which waits for
  the client's window thread to go idle.
- Item 182: the termination warning's form for several invisible figures or components, and what
  R2025b does with visible ones at termination, were not measured.
- Item 183: a WPF client's window thread waiting in `Call` cannot open the windows a component
  waits on. R2025b's windows have threads of their own, which the runtime could give them here.
