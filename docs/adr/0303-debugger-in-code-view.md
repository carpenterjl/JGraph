# ADR 0303 — The debugger in the Code View: breakpoints, `dbstop`, the RUN section's debug controls

## Status

Accepted, 2026-11-03. Stage W11 of the App Designer window plan (decision WD4): the debug words `dbstop`, `dbclear`, `dbstatus`, `dbstack`, `dbtype` and the five prompt words; each console session's own breakpoint store and debugger; App Designer's breakpoints in the Code View, the RUN section's Pause, Continue, Step, Step In, Step Out and Stop, the BREAKPOINTS and ERROR HANDLING groups; the shell's editors over the same store.

## Context

The RUN section's execution controls, the BREAKPOINTS and ERROR HANDLING groups of Run's drop-down and the code view's margin were the designer's last disabled debugging actions (W2 bound them to "not yet"; the margin was drawn and nothing listened). The shell debugged only a document run under F5, with a one-shot `JgsDebugSession` attached for that run alone (ADR 0128), and knew no `dbstop`. R2025b's App Designer, read in place: the RUN section is the rich text editor's `ExecutionControlsToolstrip` (Run, Pause or Continue in one column, Step In and Step Out shown only while debugging), the actions reach the editor's debugger (`rtc_pause`, `rtc_continue`, `rtc_step`, `rtc_debug_step_in`, `rtc_debug_step_out`, `rtc_stop_execution`, the breakpoint actions, `setDBStopIfError` and its kin), `AppModel.IsDebugging` is true while the app's file is in the debug call stack (`AppCodeTool.processDebugInfo`), and while it is, every action listening to `debuggingStateChanged` rests - Run, the insertions, Share, App Input Arguments - and `SaveAction` quits debugging before it saves. Breakpoints in an `.mlapp` count the lines of the generated class text (W0, `w0_debug`), and `dbstop`, `dbclear` and `dbstatus` were measured headless for a function file with a local function, a script, a class and the acceptance app (`w11_debug`, 60-odd calls): a line without code moves to the next executable line, a function's `end` counts, a line past the last is `MATLAB:lineBeyondFileEnd`; `file>fn` names a local function or a `Class.method`, and with a line number is refused; `dbstatus` prints "Breakpoint for name is on line N." or "Breakpoints for name are on lines N, M." with "  Breakpoint on line N has conditional expression "..."." under it, the functions sorted by name, and "Stop if error." for the conditions, "with identifier X" for one named; its struct has `name`, `file`, `line`, `anonymous`, `expression`, `cond` and `identifier`; `dbstop if error` and `dbstop if error MATLAB:x` both list `all`, clearing one identifier while all are on is `MATLAB:dbclear:cannotClearWhenAllEnabled`; the prompt words outside the debugger are `MATLAB:dbOnlyInDebugMode`; `dbtype` prints a blank line then each line under a six-wide number. Pausing itself needs a window session, so it was not measured.

## Decision

- **The store** (`Jgs/Debug/JgsBreakpointStore`): each console session's breakpoints by file and line, with a condition and an enabled flag, the four `dbstop if` conditions with their identifiers, and App Designer's Pause on Output; one `Changed` event. `dbstop`, `dbclear` and `dbstatus` (`JgsBuiltins.Debug`) work on it in R2025b's grammar and words; the shell's editors and the designer's code views show it and set it through it, so a breakpoint set at the prompt shows in the margin and one clicked in the margin is listed by `dbstatus`.
- **The lines** (`Jgs/Debug/JgsSourceMap`): a file's executable lines from its parse tree - every statement's line, a function's `end` (from the block scanner of W9b), not a `function` or `classdef` line - where a breakpoint lands, the function at a line named as `dbstatus` names it (`stem`, `stem>local`, `stem>Class.method`), and the first line of a named function.
- **The debugger** (`JgsDebugSession.Attached`): a session's own debugger, bound to each interpreter the session builds, hooked into the interpreter (`DebugHook`) while the store holds anything or a pause is wanted, and standing aside otherwise so a session without breakpoints keeps the interpreter's fast path. It pauses whatever runs in the session - a run, a statement typed at the prompt, an app's callback fired from its window - at an enabled breakpoint whose condition holds, at a step, at a Pause, at a function's `end` with a breakpoint (`FunctionReturning`), at a statement that raised an error (`StatementFailed`, `dbstop if error` for one no `try` will catch, `caught error` for one a `try` will, the interpreter counting its `try` bodies), at a warning as it is recorded (`JgsWarningState.Raised`), at a statement that assigned NaN or Inf (`AfterStatement`), or at a statement that wrote to the console (Pause on Output, the host's `OutputHook`); the conditions pause code in files only, as R2025b's do, never a statement typed at the prompt. `Quit` unwinds the paused statement with `JgsDebugQuitException`, which the session swallows quietly, as `dbquit` is quiet. A pause in an idle session's callback marks the shell's session paused and returns it to idle on resume. The one-shot run of ADR 0128 stays for an engine without a console session.
- **A class file read again** (`Interpreter.DropClassIfFileChanged`, `JgsFunctionPath.Unload`): a class defined from a file carries the file's write time, and its next mention after the file was written again loads the new text, once per statement at most; `clear name` forgets a class from a file. Before this, a class once loaded was never read again, and App Designer's Run after a save ran the old lines.
- **The designer** (`AppDesignerWindow.Debug`, `DesignDebug`): the MATLAB session's debugger comes through `IScriptDebuggerHost`; the code view's margin sets and clears breakpoints snapped to statements; Set/Clear (F12), Clear All, Enable/Disable (a disabled breakpoint drawn hollow) and Set Condition (JGraph's dialog; a conditional one drawn with a pale centre); Pause on Errors, Warnings, NaN or Inf and Output as check items over the store; Pause, Continue, Step (F10), Step In (F11), Step Out (Shift+F11) and Stop (Shift+F5, Quit Debugging while paused, the shell's Stop while the app's code runs) with the execution controls swapped as `ExecutionControlsToolstrip` swaps them; a pause in one of the designer's apps switches it to the Code View, marks the line, locks the editor, rests Run, Share, the insertions, App Input Arguments and Shift+F7, and Save quits debugging first; datatips over the paused frame's variables; the shell's Workspace and Call Stack panes show the frame as for any pause. The debugger counts the file's lines and the code view shows the class as the designer writes it again, the same line for line once this designer saved the app; before that (an app R2025b or a hand wrote) `DesignDebug.MapLines` maps the two with W14's line comparison, and the margin, the marker and the caret's commands go through it. A save writes the file again, so the breakpoints are carried across it by their place in their functions (`DesignDebug.Anchor`/`Resolve`), with the status line saying how many moved or were dropped.
- **The plain-text renderer** (`DesignPlainText.Render`): a CRLF file was given a second carriage return on every line - the join used the file's ending and then turned every line feed into it again - so the code view showed each line twice; it joins with a line feed first now. The parser's command syntax, which `dbstop if error`, `dbstop in Class>Class.method` and `dbtype f 4:6` need, follows MATLAB's rule: the first word after the name decides (a word, a literal, a keyword, an option glued to its minus), and everything after it to the end of the statement is words, whatever the tokens.

## Measured

- **Tests**: `JgsDebugWordsTests` (35: where breakpoints land and the names and order `dbstatus` prints, conditions replaced and dropped and the struct's fields, 26 refusals in R2025b's identifiers and words, what R2025b accepts silently, the `dbstop if` lines and the all-wins rule, `dbstack` and `dbtype`, a breakpoint pausing a later statement in the function's frame with `dbstack` at the K>> prompt, `dbstop if error` pausing a function's line and not a caught or a prompt error with Quit unwinding quietly, a breakpoint in the acceptance app's startup function pausing App Designer's Run with the argument in the frame), `JgsDebugReloadTests` (1: a rewritten class file runs its new lines), `DesignDebugTests` (5: executable lines and snapping, breakpoints following their callback across a rewrite, homeless anchors dropped, a CRLF and a mixed-endings plain-text app rendered once); 171 pass with the toolstrip, the older debugger, the prompt-word, the command-syntax and the app-run suites, 126 with the plain-text app suites, 124 with the file index, resolver, builtin registration, toolstrip, editor and comparison suites.
- **The window check** (`run-w11designer.ps1`, JGraph.Application in Release): all 41 checks pass - a `-r` file sets a breakpoint with `dbstop` in a hand-written plain-text app and opens it in App Designer; the Code View's margin shows the breakpoint at the file's line, mapped to the class as the designer writes it; Save writes the class back with the property line the hand left out and the breakpoint follows its function down one line; Run pauses in `W11App.startupFcn` at that line with Run gone and Continue, Step In, Step Out, Step and Stop there and enabled, the Callback insertion resting, the code view marking the line, the shell's prompt `K>>`; Step moves the pause one line; Continue finishes the run, the app's window comes up, Run is back and the prompt is `>>`; Run's drop-down's Clear All Breakpoints clears the margin, Pause on Errors toggles and stays checked when the drop-down opens again, and with the caret put on the startup function's first line through Go To, Set/Clear sets a breakpoint there. I looked at the pictures of the paused designer and of the EDITOR tab with the breakpoint set.
- **Sweep 36**: the ten names are built-ins (`exist` 5) with `nargout` 0, 1 for `dbstatus`, 2 for `dbstack`, a `file` under every argument pattern.

## Not measured

- **R2025b's own window** was not seen: the pause's look, the paused line's marker, the Enable/Disable and Set Condition dialogs; its words come from the action recording.
- **Pausing in R2025b** (`dbstack` while paused, `K>>`, the frame names, what `dbstatus` lists for a disabled breakpoint) needs a window session and was not measured; JGraph's frame names are the error stack's (`Class.method`), and a disabled breakpoint is listed as its line.
- **Several identifiers** on one `dbstop if` condition: how `dbstatus` words them was not measured ("with identifiers A, B" is JGraph's).
- **`dbstop if naninf`** is checked over what a statement assigned, not over every operation, and **Pause on Output** over what reached the console.
- **The shell's editor margins** and the Workspace pane while paused in a callback were not driven by a check; the older W2 check drives the shell's prompt.

## Divergences

- **The conditions pause code in files only**: an error, a warning, NaN or Inf or output from a statement typed at the prompt is reported, not paused at.
- **`dbstop if naninf`** looks at what a statement assigned; **Pause on Output** at what reached the console; neither is R2025b's engine.
- **`dbstatus`** prints no `opentoline` links; a disabled breakpoint is listed as a set one; several identifiers on one condition are worded as JGraph words them.
- **`dbstack`** at a pause lists the functions alone, the base workspace's statement being no frame; outside a pause it is the running functions.
- **Set Condition** is JGraph's dialog, not the rich text editor's; **Enable/Disable** and a condition are drawn as a hollow dot and a pale centre, JGraph's marks.
- **A breakpoint on a function's `end`** pauses as the function returns, not at the `end` as an executable line.
- **A class file is read again at its next mention after a write**, once per statement; R2025b's rule for a class edited while instances exist is not reproduced.
- **An app R2025b or a hand wrote** shows its breakpoints through a line map until the designer saves it; the paused line of a file line the code view does not show is said in the status line.
- **Command syntax** follows the first word, as MATLAB's rule does; `x -1` with `x` a variable stays an expression, which JGraph's parser cannot tell from a command.
