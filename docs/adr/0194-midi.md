# ADR 0194 — MIDI: mididevinfo, mididevice, midimsg, midisend, midireceive and midicontrols

## Status

Accepted. Stage D10b of the device classes plan
(`docs/plans/serialport-and-usb-device-classes-plan.md`), after ADR 0193 (143f839). It answers the
plan's open question 9 by putting MIDI in scope. One commit, this ADR's.

## Context

R2025b's MIDI functions are Audio Toolbox files, all readable MATLAB:
- `mididevinfo.m`, `mididevice.m`, `midisend.m` and `midireceive.m`;
- `midimsg.m` and `midimsgtype.m`;
- the older control-surface family: `midicontrols.m`, `midiread.m`, `midisync.m`,
  `midicallback.m` and `midiid.m`.

Under them sit the compiled `midimex` and a private `midimexif` over PortMidi. Five probes under
`tools/matlab-checklist/device-probes` measured the rest:
- `probe_midi_env`: the device list, and mididevice's checks and object;
- `probe_midi_msg`: every midimsg form, its display, properties, setters, arrays and midimsgtype;
- `probe_midi_controls`: midicontrols and its functions with no MIDI input;
- `probe_midi_scale`: midicontrols' private scaling, called from its folder;
- `probe_midi_cs`: a dot on a midimsg array where one value is wanted.

What they show:
- **Devices.** `midicontrols.devices` is PortMidi over WinMM (Interface `'MMSystem'`). It lists:
  - the MIDI Mapper as an input, when WinMM has one;
  - the inputs;
  - the MIDI Mapper as an output;
  - the outputs.

  They are numbered from 0. On this laptop that is "Microsoft MIDI Mapper" 0 and "Microsoft GS
  Wavetable Synth" 1, with no inputs.
- **A device opens once.** Two `mididevice(0)` on the MIDI Mapper both succeed, though WinMM lets one
  client open it, so midimex shares an open device. Opening the GS Wavetable Synth while the Mapper
  is open fails in both engines ("already in use"), since the Mapper holds the synth underneath.
- **midimsg is a value class** with object arrays: `midimsg('Note', …)` answers a 2-by-1,
  `midimsg(n)` an n-by-n. It indexes, grows, deletes and joins as any array does.
  - `[a; 1]` converts the 1 through the constructor.
  - `q = []; q(1) = midimsg` cannot convert. A variable that does not exist yet grows into a midimsg
    array.
  - A dot on an array is a comma-separated list. Where one value is wanted it is the first
    (`v = a.Timestamp`).
- **Names.** SetProhibited names the class `''midimsg''` from inside a function.
- **midicontrols scaling.** Raw r reads r/126 up to 63 and (r−1)/126 above. A value x is written
  as round(x·126), one more above 63. So 0.5 is raw 63 and reads 0.5, and raw 64 also reads 0.5.
- **midiread has one output.** `nargout('midiread')` is 1; `[v, c] = midiread(mc)` is refused.

## Decision

### The device layer (JGraph.Devices.Midi)

**`WinMmMidi`** lists devices in PortMidi's order and opens them through WinMM:
- the MIDI Mapper is `MIDI_MAPPER` (0xFFFFFFFF);
- an input's short messages come through the driver's callback;
- a system exclusive message comes through four 4 KiB buffers, each handed back to the driver from
  another thread, as WinMM requires.

**Timestamps** are seconds on `MidiClock`, which starts the first time anything in the process asks
it the time.

**`MidiScheduler`** sends an output's messages at their times, so `midisend` returns at once:
- each message goes on a thread of its own at its time, ties kept in the order given;
- the system timer runs at 1 ms while a message is pending, so a note is late by about a millisecond
  rather than a 15.6 ms tick;
- closing an output drops what it has not sent and resets the device, which turns off any note still
  sounding.

**On the wire:**
- channel and system messages are short messages;
- SystemExclusive, the Data messages after it and EOX are one long message, sent at the
  SystemExclusive's time;
- a received system exclusive message comes back as SystemExclusive, Data in chunks of eight
  (an F4 terminus after a short last chunk) and EOX, as midimsg builds them.

**Sharing.** Every open device is shared by all its holders and closes with the last
(`MidiShared.OpenInput` and `OpenOutput`).

**`SimulatedMidi`**, behind `jgraph.internal.midisim('on')`:
- an input and an output both named "JGraph Loopback", where what the output sends arrives at the
  input when it is due;
- an output "JGraph Sink" that keeps what it is sent (`midisim('sent')`).

Nothing is heard.

### Arrays of external values

A new kind of script value, `IJgsExternalArray`, is a 2-D array of one class's values that is never
changed in place. The interpreter indexes it through a proxy: a double array of the same shape
holding each element's position. Subscripts, `end`, masks, `a(i) = []` and growth all run through
the ordinary numeric code on the proxy, and the positions it returns say which elements the answer
holds. Around that:
- A write builds the new array and rebinds the variable: `a(i) = b`, `a.p = v` and `a(k).p = v`
  (growing when k is past the end), plus `c{k}.p = v` and `s.m.p = v`.
- `[a.p] = deal(v)` expands to one target per element, as a struct array's field does.
- A bracket joins arrays of the class. A double is converted through the class; an empty double is
  left out.
- A `for` loop walks the columns.
- An echo prints "name =" and then the class's own disp (`IJgsOwnDisp`), as it does for a classdef
  that defines disp.

As methods of the class (the M145 user-method layer): `size`, `numel`, `length`, `isempty`, `ndims`,
the `is…` shape questions, `isequal`, `repmat`, `reshape`, `transpose`, `horzcat`, `vertcat`, `cat`,
`num2cell`, `arrayfun` (as `cellfun` over the elements), `disp`, `properties` and `methods`.

### The script surface

- **`midimsg`** is transcribed from midimsg.m. Each element keeps eight raw bytes and a timestamp:
  - the constructor's `validateattributes` and `validatestring` checks, in their order and words;
  - get.Type through DecodeMidiByte and DecodeChannelModeByte, NumMsgBytes and MsgBytes;
  - the type-specific properties and the refusal for the others, and every set method;
  - Timestamp's `(1,1) double`;
  - description and disp.
- **`midimsgtype`** is an array of members over int32:
  - `midimsgtype.NoteOn` and `midimsgtype(1)`;
  - `==` against members, a name or numbers, element by element;
  - int32 order and arithmetic, `double` and the other conversions, `char`, `string`, `cellstr`;
  - `ismember`, `isenum`, `switch`, and `enumeration('midimsgtype')`.

  So `list([list.Type] == midimsgtype.NoteOn)` picks the note-ons out of a list.
- **`mididevinfo`** answers the struct, or prints mididevinfo.m's table when no output is asked for.
  `midicontrols.devices` answers its struct array.
- **`mididevice`** is transcribed from parseArgs and validateDevice:
  - read-only Input, Output, InputID and OutputID;
  - `get` and `set` refused, as for a plain handle class;
  - the hidden send, receive and hasdata.
- **`midisend`, `midireceive`, `midiread`, `midisync` and `midicallback`** call their first argument's
  method, or refuse it in R2025b's words.
- **`midicontrols`** is transcribed from midicontrols.m:
  - its inputParser, with the validators' refusals wrapped as the parser wraps them;
  - its device lookup and its two warnings;
  - its disp, and the hidden midiinfo;
  - `midicontrols.trace`.

  With a device, each control follows the control changes of its number and channel (channel 0 for
  any, no number for any control). midisync sends to the output of the input's name. midicallback
  runs `cb(mc)` at the device queue's drain points when a change has moved the values.
- **`midiid`** warns and answers empty with no input; with inputs, it waits for a control change on
  any of them.

## Measured

Two fixtures are recorded from R2025b; both agree in both representations:
- **`midi_msg`** (217 rows): pure values, and every row agrees.
- **`midi_devices`** (108 rows): this machine's devices, opening outputs and never sending. One row
  is a stamped divergence (below).

One fixture is JGraph-only:
- **`midi_sim`** (25 rows), on the simulated devices, written from the rule. It covers round trips,
  timestamp order, the note pair, system exclusive both ways, midireceive's limits, the loopback and
  sink, midicontrols with each kind of control, midisync through the loopback, midicallback's calls,
  and midiid.

`tests/JGraph.Tests/Devices/MidiTests.cs` adds 6 unit tests:
- the list in PortMidi's order;
- the scheduler's order and timing;
- the loopback and the sink;
- a system exclusive message on the wire and back;
- a shared output;
- midicontrols' scaling.

On this laptop JGraph's `mididevinfo` matches R2025b's line for line.

**Live check (2026-09-29).** A ten-second piece played through `midisend` on the GS Wavetable Synth:
124 messages in one call, three programs, reverb, arpeggios, a pad and a bass. The user heard it
play correctly. It is kept as `examples/midi_tune.m`, which also passes R2025b's checkcode and builds
the same 124 messages there.

## Live checks for the user

- A USB-MIDI keyboard or controller, or the STM32 board's MIDI interface when its firmware has one:
  - `midireceive` of played notes;
  - `midicontrols` following a knob, and `midicallback` on it;
  - `midiid`;
  - `midisend` to the device.

## Divergences

- **A one-sided mididevice's other name** (`d.Input` of an output) is 0-by-0 in JGraph and 1-by-0 in
  R2025b, since `''` is 0-by-0 in JGraph (`midi_devices`, `dev_input_size`, div=ADR0194).
- **Echoes** print "m =" and the disp lines in JGraph's layout, without R2025b's blank lines.
- **A dot on a midimsg array** as a bare statement shows the first value, where R2025b shows each as
  ans. Inside an operator (`a.Timestamp + 1`) JGraph uses the first value, where R2025b refuses the
  list.
- **Not provided:**
  - `struct(msg)`, which R2025b answers with a warning;
  - midimsg's hidden statics (toStruct, fromStruct, sortStructsByTimestamps) and hidden constants
    (DecodeMidiByte, DecodeChannelModeByte);
  - `char` of more than one midimsgtype member;
  - arrays of more than two dimensions.
- **`midicontrols.trace`** keeps its state and prints no trace lines.
- **Unmeasured choices, made because no MIDI input is attached here:**
  - Data outside a SystemExclusive…EOX frame is not sent.
  - Closing a device drops what it has not sent and resets it.
  - midireceive answers an N-by-1 column (0-by-0 when nothing came, as fromStruct answers).
  - A specific control's last control is the last change it followed.
  - midisync pairs an input with the output of its name.
  - midicallback runs when a change arrives rather than on a 0.05 s poll.

## Still open

- Windows MIDI Services (MIDI 2.0) is not used; WinMM reaches every MIDI 1.0 device R2025b lists.
- `struct(obj)` of a value object, and a bare comma-separated list as a statement showing every
  value (chips file).
