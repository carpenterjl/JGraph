# 0100 — A library function is a third population

Date: 2026-08-28 · Status: accepted (M99; toolbox-function arc, item 1)

## Context

`fminsearch` was not missing. It was **refused**:

```csharp
["fminsearch"] = "optimization",
```

— one row in `UnsupportedFunctions`, sitting beside `fmincon` and `lsqcurvefit` since M35, so that a
script asking for it got a sentence rather than a baffling "not recognized". That row was wrong in a
way nobody had reason to notice: `fmincon` and `lsqcurvefit` belong to the Optimization Toolbox and
`fminsearch` does not. It ships with base MATLAB, in `toolbox/matlab/optimfun`, next to `fminbnd`,
`fzero`, `lsqnonneg`, `optimset` and `optimget`.

The deeper reason it went unnoticed is that **no number here could move when it was fixed**.

MATLAB's `toolbox/matlab` tree holds 1,759 `.m` files at depth two, and they are two different
things:

| Kind | Count | `which` says | What the `.m` holds |
|---|---:|---|---|
| built-in | 518 | `built-in (…)` | help text only; the code is in the MATLAB kernel |
| MATLAB-code function | 1,241 | a file path | real MATLAB source, interpreted like a script's own |

`fminsearch` is the second kind. `exist('fminsearch')` answers 2, not 5. So are `fzero`, `ode45`,
`spline`, `roots` and `integral` — most of what a person means by "MATLAB".

And every coverage document in this repository was blind to that category:

- `matlab-builtin-coverage.md` counts the 514 commands documented with kind **builtin**. None of
  these names is one.
- Its second table counts the 277 graphics commands documented with kind **function**. None of these
  is graphics.
- `matlab-form-coverage.md` measures exactly those two populations together, and its prober says so
  in its own filter: `kind == "builtin" or (kind == "function" and graphics == "yes")`.

The consequence, measured for the first time in this milestone: **`funfun` stood at 1 name of 40 and
`optimfun` at 0 of 6, and no headline in the repository would have changed by a digit if either had
gone to zero or to full.** The one figure that did cover them — "927 of 2,024 across every callable
kind" — is a single number over five kinds at once, which is why nine milestones of `datafun` work
and an untouched `sparfun` looked the same from outside.

This is not the first time it was seen. `docs/architecture.md` has said since M24 that an audit of
ninety documented call forms "found seven everyday names missing that **no coverage arithmetic could
have reported**, because the tables track builtins and graphics functions and these are documented as
plain functions." Seven names were fixed and the arithmetic was not, so the same hole swallowed the
next seventy-five milestones' worth of the same category.

## Decision

**The mathematical library functions are a third population, and they are measured as one.**
`docs/matlab-toolbox-coverage.md` counts the non-graphics `function`-kind commands of the sixteen
mathematical folders, **by MATLAB toolbox folder** — because that is the unit they arrive in and the
unit a milestone takes on. It is generated by `tools/matlab-checklist/probe-toolbox-forms.py`, which
reuses `probe-forms.py`'s samples, batching and five verdicts wholesale and differs from it only in
the filter, and it is checked by `verify-toolbox-coverage.py`, the fifth exit-code gate.

It opens at **172 of 377 names and 225 of 1,036 documented forms**, with `optimfun` at 6 of 6.

**These names are implemented in C#, in the tier every other name is in.** Not as shipped `.m` files
on the function path, which JGraph has had since M62 and which is how MATLAB itself does it. Three
reasons, and the first is not performance:

1. Every piece of this repository's bookkeeping reads the registration table.
   `JgsCompletionTests.Catalog_MatchesTheLiveBuiltinRegistration_Exactly` compares
   `JgsScriptEngine.BuiltinNames()` against `JgsBuiltinCatalog.cs`; all five verifiers and both
   probers read the same file. A shipped `.m` tier is invisible to all of it and would need a
   parallel apparatus before it could be counted at all.
2. `JGraph.Statistics.Optimize.NelderMead` already existed. For this folder, C# was *less* code than
   a port, not more.
3. A shipped tier needs `private/` folders, `+package` resolution, an implicit install path, a
   startup parse-and-cache story, and a shadowing rule on top of ADR 0062's recorded "a builtin
   beats a file of the same name". None of that is work this milestone needed to do.

Performance is the weakest of the arguments and is recorded honestly: for a *driver* like
`fminsearch`, the run time is dominated by evaluating the caller's objective, which is interpreted
either way, so the ceiling on a C# rewrite is small. For anything touching whole arrays it is not
small at all, and M98's loop compiler does not rescue an interpreted kernel — it refuses any indexing
and any call, which is what such a body is made of.

**The algorithms are the published ones, taken from the papers the MathWorks sources themselves
cite** — Nelder and Mead by way of Lagarias, Reeds, Wright and Wright (1998); Brent's `fmin` and
`zeroin` by way of Forsythe, Malcolm and Moler (1976); Lawson and Hanson (1974) for the non-negative
least squares. Four new files under `src/JGraph.Numerics/Optimization/`, which is a leaf project both
`JGraph.Statistics` and `JGraph.Scripting` already reference.

**`SimplexSearch` is a second Nelder–Mead, deliberately.** `JGraph.Statistics.Optimize.NelderMead`
serves three distribution fitters and differs from MATLAB in six ways that are invisible to a fitter
and visible to a script: it folds a NaN objective to +∞; its tolerances are relative where MATLAB's
are absolute and floored at ten ulps; it tests convergence before the first iteration rather than at
the top of the loop; it accepts an outside contraction on `<` where MATLAB uses `<=`; it re-orders by
insertion after a single replacement where MATLAB re-sorts all n+1 stably; and its defaults are 1e-8
where MATLAB's are 1e-4. `output.iterations` and `output.funcCount` are answers a script reads, so
the counting convention is part of the contract. Changing that class to serve one caller would have
moved three.

### Divergences recorded here

The first of these narrows a rule ADR 0062 set; the rest are differences this milestone accepts.

- **An error whose identifier MathWorks documents is raised with that identifier, where ADR 0062
  left every runtime error's identifier empty.** That ADR's reasoning was that a spelling MATLAB
  does not use would make a script's `catch` branch wrongly on the real thing, and it does not reach
  a *published* identifier. `MATLAB:fminsearch:NotEnoughInputs` is written in MathWorks' own source
  and its message is in `resources/MATLAB/en/optimfun/fminsearch.xml`; a
  `strcmp(ME.identifier, …)` against it branches the same way on both engines, which is the outcome
  ADR 0062 wanted. Nineteen identifiers were checked against MATLAB R2024a by running the same
  script through both, and all nineteen match. An identifier JGraph would have to invent is still
  left empty.
- **`optimset` holds eight fields where MATLAB's holds some sixty when a toolbox is licensed.**
  MATLAB's own `optimset` grows when `license('test','Optimization_Toolbox')` passes and shrinks to
  exactly these eight when it does not, so this is base MATLAB's answer. The visible consequence is
  that `optimget(opts, 'Tol')` reports two ambiguous names here and eight on a machine with the
  toolbox.
- **`Display` of `'simplex'` is read as `'iter'`.** It is `fminsearch`'s undocumented fifth level,
  which dumps the whole simplex each iteration in a display format it also changes globally. It is
  accepted rather than refused, and reads as the documented level nearest it.
- **An objective given as an expression in text is not accepted.** MATLAB's `fcnchk` builds an
  `inline` object from `'x^2'`; `inline` is obsolete in MATLAB and absent here. A handle, or the
  name of a function, both work.

## What this did not close, and what it cannot

- **The form prober can build 8 of optimfun's 30 forms.** Not a gap in the build: it has no sample
  for an `options` structure or a `problem` structure, and its generic `@sin`/`[1 2 3]` samples are
  correctly refused by `fminsearch` (a vector objective is not scalar) and by `lsqnonneg` (a 2×3 `C`
  against a 3-element `d`). MATLAB refuses them identically. **All 30 forms were therefore run by
  hand, one line each, through both engines and diffed** — every one works and every numeric answer
  agrees. Improving the shared samples would move `matlab-form-coverage.md`'s numbers as a side
  effect of this milestone, so it was left for a milestone that owns it.
- **`fmincon` and `lsqcurvefit` stay refused**, with their reasons corrected to name the
  Optimization Toolbox. They are not base MATLAB and are not this arc's business.
- **A transcendental objective can cost one iteration more than MATLAB.** `exp(1.6094379124341003)`
  is exactly 5 in MATLAB and 4.9999999999999991 in .NET — one ulp — so `fzero(@(t) exp(t)-5, 0)`
  takes 8 iterations here against MATLAB's 7 and lands one ulp away. This is a libm difference that
  predates the milestone; the two engines agree to the digit on every polynomial objective tested,
  iteration and evaluation counts included.
- **Two defects were found in passing and left standing.** An indexed append to a **global cell**
  inside a function (`c{end+1} = s`) silently does nothing, while the same append to a global
  numeric array works and a whole-value reassignment of a global cell works; MATLAB does all three.
  And `sort` refuses a cell array of character vectors, which MATLAB sorts alphabetically. Both were
  hit while writing this milestone's tests, both are older than it, and both are worked around in
  the tests rather than fixed here. *The global-cell one has since been fixed: every indexed write
  that rebuilds its container now rebinds in the workspace a `global` declaration names rather than
  in the frame that ran it. The `sort` one still stands.*

## Consequences

- Four new engines under `src/JGraph.Numerics/Optimization/` — `SimplexSearch`, `BoundedMinimizer`,
  `RootFinder`, `NonnegativeLeastSquares` — over a shared `SearchWatcher` seam that lets a display,
  a plot and a script's own output function watch a solve and stop it. `JGraph.Numerics` gains a
  folder and no dependency; it is still a leaf.
- Three new scripting partials (`JgsBuiltins.Optimize.cs`, `.Solvers.cs`, `.Display.cs`) and one
  registration line in `CreateGlobals`. Nine names in the catalog: the six documented ones and
  `optimplotfval`, `optimplotx`, `optimplotfunccount`, which have no documented syntax table because
  a solver calls them, and without which `optimset('PlotFcns', …)` names nothing.
- **One interpreter change, five lines.** A builtin that both calls itself when mentioned bare
  (`AutoCallsBare`) and cares whether anyone wanted the answer (`KnowsWhenDiscarded`) is now told
  that nobody did, exactly as a written-out call already was. Only `optimset` sets both today. Before
  it, `optimset` on its own line echoed `ans = struct(…)` where MATLAB prints the settings.
- `docs/matlab-toolbox-coverage.md` and two new tools; `matlab-builtin-coverage.md` gains six
  (927 → **933** across all kinds) and **has its stale blockquote corrected**: it had been quoting
  the form sweep as 1,011 of 2,422 since M69, where the sibling document it points at says 1,344 of
  2,454. Six milestones had moved that number and nothing had re-read it.
- Tests move from 5,916 to **5,953**, all green, with 0 build warnings. All five coverage verifiers
  exit 0.

## Testing

`tests/JGraph.Tests/Scripting/MatlabOptimizeM99Tests.cs`, 37 cases, assertions inside the scripts.

- **fminsearch (9)** — the answer, the starting point's shape preserved through the objective and
  back (row, column and matrix), MATLAB's exact iteration and evaluation counts on two problems,
  both budget exits and their messages, the problem structure, a problem structure built for another
  solver, trailing arguments reaching the objective, and a non-double start.
- **fminbnd (5)** — the answer and counts, a parabola's vertex hit exactly, bounds the wrong way
  round, bounds that are not finite scalar doubles, a non-scalar objective.
- **fzero (5)** — a bracket, an outward search with its interval-iteration count, an end that is
  already a zero, three refusals, and the −3 and −5 exits.
- **lsqnonneg (3)** — a binding constraint pinned to exactly zero, an unbound answer left alone, the
  two refusals, and every output's shape.
- **optimset / optimget (5)** — the eight fields in order, each solver's defaults including the two
  stored as text, merging and altering, prefix matching, and three refusals.
- **Display and callbacks (8)** — `'iter'` prints its table, `'notify'` is silent on success,
  `'off'` is silent on failure, an output function stops the solve, the states and the
  `optimValues` fields for both a minimize and a zero find, `FunValCheck`, the plot functions
  drawing, and `fminsearch` no longer being refused as unsupported.

Two tests were written around defects older than this milestone rather than through them: the global
cell append and `sort` of a cellstr, both noted above.

## Live checks for the user

Batch cannot confirm these:

- `fminsearch(@(v) sum((v-[1 2]).^2), [0 0], optimset('PlotFcns', @optimplotfval))` draws a figure
  that gains a point per iteration while the solve runs.
- The same with `@optimplotx` draws one bar per unknown and redraws them as the search moves.
