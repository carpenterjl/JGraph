# ADR 0191 — DFU 1.1 and ST's DfuSe over WinUSB, as jgraph.usb.dfu

## Status

Accepted. Stage D8 of the device classes plan
(`docs/plans/serialport-and-usb-device-classes-plan.md`), after ADR 0190 (490bfbd). One commit,
this ADR's.

The stage adds these names under `jgraph.usb`, all JGraph extensions with no MATLAB counterpart:
- `dfulist` and `dfu`: firmware update over the USB Device Firmware Upgrade class;
- `dfufile` and `dfusuffix`: the firmware files it sends.

## Context

DFU is how a board's USB bootloader takes new firmware. Two kinds matter to the plan:
- the STM32 board's ROM loader, which speaks ST's DfuSe (bcdDFUVersion 1.1a);
- any TinyUSB firmware with a DFU run-time interface that detaches into a loader.

dfu-util is the reference host. It reaches a device through libusb, which reaches it through WinUSB
on Windows, so JGraph uses D7's WinUSB layer directly. DFU needs only the default control pipe.

Firmware comes in four forms:
- a raw `.bin`;
- a `.dfu`: the image with DFU 1.1's 16-byte suffix, which carries the IDs it is for and a CRC;
- ST's DfuSe container, holding targets per alternate setting and elements at addresses;
- Intel HEX.

This laptop has one DFU interface: the webcam's run-time interface (13D3:56EB, interface 4), which is
bound to WinUSB. It is listed and never sent a request, not even GETSTATUS.

## Decision

### The protocol (JGraph.Devices.Dfu)

`DfuDevice` sends the seven class requests of DFU 1.1 over an `IDfuTransport`. That is the control
pipe: WinUSB (`WinUsbDfuTransport`) or the simulator. Every operation starts as dfu-util's does,
bringing the device to dfuIDLE:
- CLRSTATUS from dfuERROR;
- ABORT from a half-finished transfer.

Each download block is followed by GETSTATUS, waiting the bwPollTimeout the device asks between
tries. A status other than OK stops the transfer with the status and state named as the
specification names them ("errPROG in dfuERROR while writing block 2").

**Plain DFU** sends the image in blocks from 0, then the zero-length block that starts
manifestation. A device that is not manifestation tolerant may reset there, and that is not a
failure. An upload runs until a short block.

**DfuSe** follows AN3156 and dfu-util's dfuse.c:
- commands go in block 0 and run on the GETSTATUS after them: set address pointer, erase page, mass
  erase, read unprotect;
- data goes in block 2 after its own address pointer, one pointer per block, as dfu-util sends it;
- leaving is the pointer, then a zero-length block.

Before writing, every page the image touches is erased, if its segment is erasable.

**Memory layouts.** A DfuSe loader describes its memory in each alternate setting's interface
string, for example `@Internal Flash  /0x08000000/04*016Kg,01*064Kg`. `DfuSeLayout` parses it as
dfu-util does:
- page runs with a unit of none, K or M;
- a letter whose bits mean readable, erasable and writeable.

Page sizes come from the layout, not a fixed number. A write outside writeable memory is refused
before anything is sent.

**Files.** `DfuFiles` reads:
- the suffix, with dfu-util's CRC (CRC-32 from 0xFFFFFFFF, no final inversion);
- the DfuSe container, with a writer for the tests;
- Intel HEX (extended segment and linear addresses; contiguous runs gathered into elements);
- raw binary.

### The script surface

- `T = jgraph.usb.dfulist(filters)` lists every device with a DFU interface from its descriptors
  alone. Columns: IDs, Mode (`"dfu"` or `"runtime"`), Version, Interface, Alternates, TransferSize,
  CanDownload, CanUpload, WinUSB (whether it is bound), Memory (the layouts), Location and InstanceID.
- `d = jgraph.usb.dfu()` opens the one device with a DFU interface. It also takes a row, an instance
  ID, or filters among those devices.
  - Properties: Mode, Version, DfuSe, Alternate (settable, sends SET_INTERFACE), AlternateNames,
    Layout (a table), the functional descriptor's fields, Location and Timeout.
  - Methods: status, download, upload, erase, massErase, readUnprotect, leave, clearStatus and abort.
    `d2 = detach(d, Wait=s)` detaches a run-time interface and waits for a DFU-mode device on the
    same hub port (Location, since a loader often has other IDs), then opens it.
- `download(d, file|bytes, Address=, Alternate=, Force=, Verify=, Progress=@fcn)`.
  - A DfuSe container sends each target to its own alternate setting. `Alternate=` narrows it to one.
  - A HEX file places its own elements, so Address with one is refused.
  - A raw image with no address goes at the start of its alternate setting's memory.
  - Verify reads each piece back. For plain DFU that is after manifestation, so Verify is refused on a
    device that is not manifestation tolerant.
- `upload(d)` reads, for DfuSe, the readable memory from Address; for plain DFU, the whole image.
- `img = jgraph.usb.dfufile(path)` answers what download would send.
- `bytes = jgraph.usb.dfusuffix(payload, VendorID=, ProductID=, Release=)` appends a suffix, as
  `dfu-suffix -a` does.

**Safety, as dfu-util does it.** Nothing is sent when:
- the file's suffix CRC fails (always refused);
- its IDs name another device, unless `Force=true`;
- an address is outside writeable memory;
- a plain device is given an address or a file in pieces.

Writing firmware is what the script asked for, as with fwrite, so nothing asks again.

**Not done:**
- `reset(d)`: WinUSB has no port reset, and cycling the device needs administrator rights. A plain
  DFU 1.1 device therefore leaves DFU mode by being replugged; `leave` says so.
- A run-time interface without bitWillDetach: `detach` warns that the device waits for a reset.

### The simulator

`SimulatedDfu` keeps DFU 1.1's state machine as requests arrive. A refused request stalls and moves
the device to dfuERROR with errSTALLEDPKT, as appendix A says. It comes in three kinds:
- a DfuSe loader shaped like ST's ROM one: 128 KiB of flash at 0x08000000 in 16 and 64 KiB pages,
  which programs only 1 to 0 (so a write to an unerased page reports errPROG), and 16 option bytes as
  alternate 1;
- a plain loader that is manifestation tolerant;
- a run-time interface that detaches into the DfuSe loader on the same port.

It carries a configuration descriptor and strings, so a simulated object is opened through the same
descriptor path as a real one. `jgraph.internal.dfusim` is the test-only door:
- `'dfuse'`, `'dfu'` or `'runtime'` for a new device;
- `'peek'`, `'image'`, `'state'` and `'gone'` to look past the loader;
- `'fail'` to make a write report errWRITE.

## Measured

- **Fixture**: `dfu_smoke` (40 rows), JGraph-only and written from the rule. It agrees in both
  representations. It covers:
  - the no-device and no-DFU refusals;
  - properties and the layout table;
  - a verified download across a page boundary that erases the old application's page;
  - Progress;
  - the default address, option bytes through alternate 1, and a HEX file;
  - the wrong-device, Force, any-device and damaged-CRC files;
  - a failed write and the recovery after it;
  - erase, massErase and leave;
  - plain DFU's round trip and refusals;
  - the run-time refusal and detach;
  - dfufile and dfusuffix.
- **Unit tests**: `tests/JGraph.Tests/Devices/DfuTests.cs` adds 9:
  - the CRC against the CRC-32 check value;
  - suffix, DfuSe container and Intel HEX round trips;
  - the F4 layout string;
  - DfuSe download, erase, option bytes, upload and leave;
  - errPROG and errWRITE with recovery;
  - plain DFU manifestation;
  - run-time detach.
- **On this laptop** `jgraph.usb.dfulist` lists the webcam's run-time interface: DFU 1.10, transfer
  size 4096, bound to WinUSB, at 2-8.

## Live checks for the user

- The STM32 board in its ROM DfuSe loader (BOOT0 high; 0483:DF11), once WinUSB is bound to it (Zadig,
  or STM32CubeProgrammer's driver): dfulist's Memory column, upload of the flash, and a download with
  Verify of a known image built for the board. Then leave, and the application runs.
- The TinyUSB firmware's DFU run-time interface: `d2 = detach(d)` finds the loader on the same port.

## Divergences

None: the names have no MATLAB counterpart.

## Still open

- **DfuSe read protection**: a readout-protected STM32 answers errTARGET or stalls the upload. dfu-util
  reports this; JGraph reports the device's status, and `readUnprotect` (which erases everything) is
  left to the script.
- **Several DFU interfaces** on one device: the first is taken.
